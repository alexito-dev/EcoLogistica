## 2. Objetivo y restricciones de decisión

Seleccionar un stack viable para un PMV web de 14 semanas, desarrollado por cinco integrantes a tiempo parcial, que gestione hasta 1,000 pedidos diarios y 50 vehículos, ejecute VRPTW/Green VRP, opere en conexiones 2G/3G y cumpla criterios de seguridad, accesibilidad, mantenibilidad y sostenibilidad.

La evaluación respeta **RES-06**: backend Python con FastAPI o Django, frontend React.js o Vue.js, PostgreSQL y cartografía Leaflet/OpenStreetMap. Por ello se comparan combinaciones permitidas; no se evalúan alternativas incompatibles como plataformas propietarias o un backend principal en otro lenguaje.

## 3. Criterios y método

Escala: **1 deficiente**, **2 bajo**, **3 aceptable**, **4 bueno**, **5 excelente**. La puntuación ponderada se calcula como `Σ(peso × puntuación) / 100`. Un stack queda descartado si incumple una restricción obligatoria, independientemente de su puntaje.

| ID | Criterio | Peso | Qué se evalúa |
|---|---|---:|---|
| CT-01 | Ajuste funcional y científico | 25 % | API geoespacial, optimización Python, tareas intensivas y mapas |
| CT-02 | Curva de aprendizaje del equipo | 15 % | Facilidad de adopción dentro del calendario académico |
| CT-03 | Comunidad y soporte | 10 % | Documentación, madurez, bibliotecas y mantenimiento |
| CT-04 | Productividad y mantenibilidad | 15 % | Tipado, pruebas, modularidad, documentación y velocidad de entrega |
| CT-05 | Rendimiento y escalabilidad | 15 % | RNF-01, concurrencia, separación del motor y crecimiento a 1,000 pedidos |
| CT-06 | Eficiencia energética | 10 % | Cómputo evitado, peso del cliente y capacidad de medir consumo |
| CT-07 | Operación, costo y portabilidad | 10 % | Código abierto, contenedores, despliegue, observabilidad y costo |

## 4. Alternativas evaluadas

### Alternativa A — React + FastAPI + PostgreSQL/PostGIS

- **Frontend:** React, Vite, TypeScript, CSS, Leaflet y OpenStreetMap.
- **Backend:** Python, FastAPI, Pydantic y SQLAlchemy/Alembic.
- **Optimización:** módulo Python desacoplado con OR-Tools y metaheurística propia; cola de trabajos solo si la medición lo exige.
- **Datos:** PostgreSQL con PostGIS.

Ventajas: integración directa con el ecosistema científico de Python; contratos OpenAPI automáticos; validación tipada; cliente construido como archivos estáticos; separación clara entre API y trabajo de optimización. Riesgos: FastAPI aporta menos funciones administrativas incorporadas que Django; el equipo debe definir explícitamente autenticación, permisos y estructura. Mitigación: plantilla por módulos, revisión arquitectónica y librerías maduras.

### Alternativa B — React + Django/DRF + PostgreSQL/PostGIS

- **Frontend:** React, Vite, TypeScript, Leaflet y OpenStreetMap.
- **Backend:** Django y Django REST Framework.
- **Optimización:** servicio Python invocado por tareas de fondo.
- **Datos:** PostgreSQL con PostGIS/GeoDjango.

Ventajas: administración, ORM, autenticación y convenciones maduras; buena opción para CRUD y gobierno de datos. Riesgos: mayor superficie y consumo base para un PMV orientado a API; integración asíncrona y separación del motor requieren más configuración; riesgo de construir funciones no necesarias. Es sólida, pero menos ligera para el alcance y plazo actuales.

### Alternativa C — Vue + FastAPI + PostgreSQL/PostGIS

- **Frontend:** Vue 3, Vite, TypeScript, Pinia, Leaflet y OpenStreetMap.
- **Backend y datos:** iguales a la alternativa A.

Ventajas: interfaz progresiva, componentes concisos y buen rendimiento; conserva la afinidad Python del motor. Riesgos: introduce un segundo ecosistema frontend frente a React, ya declarado en el README; el costo de realinear documentación, aprendizaje y convenciones reduce la ventaja durante 14 semanas.

## 6. Decisión

Se selecciona la **Alternativa A: React + Vite + TypeScript + Leaflet/OSM; FastAPI + Python; PostgreSQL + PostGIS**. Es la combinación de mayor puntuación y coincide con la arquitectura declarada en el repositorio. Su ventaja decisiva es mantener el motor VRPTW/Green VRP y la API en el ecosistema Python, con un frontend independiente y ligero.

### 6.1. Componentes de la línea base

| Capa | Selección | Responsabilidad |
|---|---|---|
| Presentación | React + Vite + TypeScript | SPA responsiva, modo conductor, dashboard y formularios |
| Cartografía | Leaflet + OpenStreetMap | Visualización de rutas, paradas, capas de riesgo y congestión |
| Estado y datos cliente | TanStack Query; estado local de React | Caché, reintentos y sincronización sin sobredimensionar la solución |
| API | FastAPI + Pydantic | Contratos REST, validación, autenticación y documentación OpenAPI |
| Persistencia | SQLAlchemy + Alembic | Acceso a datos y migraciones versionadas |
| Base de datos | PostgreSQL + PostGIS | Integridad transaccional, geometrías, índices espaciales y consultas geográficas |
| Optimización | Python + OR-Tools como base + metaheurística propia | Construcción, mejora y validación de soluciones VRPTW/Green VRP |
| Reportes | Generación PDF del lado servidor | Informes reproducibles con metodología y metadatos |
| Pruebas | Pytest; Vitest; Playwright | Unidad, integración, interfaz y aceptación |
| Calidad/seguridad | Ruff, mypy, ESLint, auditoría de dependencias, SAST/DAST | Puertas automáticas de calidad y OWASP |
| Empaquetado | Docker Compose para desarrollo | Entornos reproducibles y portables |
| Automatización | GitHub Actions | Pruebas, análisis y construcción por pull request |

Las versiones concretas se fijarán en archivos de dependencias y se aprobarán mediante pull request después de comprobar compatibilidad y soporte; este documento no congela números de versión susceptibles de quedar obsoletos.

## 7. Arquitectura de ejecución

```text
Navegador/PWA
  └─ React + Leaflet
       └─ HTTPS / REST
            └─ FastAPI
                 ├─ Servicios de pedidos, flota, usuarios y reportes
                 ├─ Orquestador de optimización
                 │    └─ Motor Python VRPTW / Green VRP
                 ├─ Calculador de CO₂ y TCO
                 └─ PostgreSQL + PostGIS
```

El cálculo pesado no se ejecutará dentro del navegador. En el PMV puede operar como módulo de backend con límites de tiempo; si las pruebas revelan bloqueo o necesidad de paralelismo, se extraerá a un trabajador asíncrono sin cambiar el contrato REST.

## 8. Decisiones de sostenibilidad

| Decisión | Efecto esperado | Evidencia |
|---|---|---|
| Servir el frontend como archivos estáticos comprimidos | Menor cómputo del servidor y transferencia | Tamaño de bundle y bytes por sesión |
| Carga diferida de mapa, gráficos y módulos no críticos | Mejor operación 2G/3G y menos datos | Lighthouse y perfil de red |
| Cachear cartografía conforme a términos de uso y no recargar capas sin cambios | Menos solicitudes y transferencia | Métrica de aciertos de caché |
| Índices GiST y consultas espaciales acotadas | Menor tiempo de CPU y E/S | Planes de consulta y latencia |
| Semilla constructiva, límite de tiempo y parada temprana del optimizador | Evitar generaciones con mejora marginal | CPU-segundos por optimización y calidad alcanzada |
| Trabajos asíncronos solo cuando las pruebas los justifiquen | Evitar infraestructura ociosa | Utilización y tiempos de cola |
| Entornos apagables y dimensionamiento por medición | Reducir costo y energía fuera del horario 05:00–22:00 | Horas de cómputo y utilización |
| Medir intensidad de carbono del software por versión | Hacer verificable la mejora | Energía/CPU por caso y gCO₂e estimados |

La sostenibilidad no se presume por usar código abierto: se comprobará comparando consumo de recursos y calidad de solución sobre el mismo dataset.

## 9. Seguridad, accesibilidad y continuidad

- HTTPS, contraseñas con algoritmo resistente, tokens de corta duración y autorización por rol.
- Secretos únicamente en variables de entorno; nunca en el repositorio.
- Validación de entrada, consultas parametrizadas, límites de carga, registro de auditoría y mitigación del OWASP Top 10.
- Componentes semánticos, navegación por teclado, contraste y pruebas WCAG 2.1 AA.
- Diseño responsive y caché de la última ruta para el modo conductor; sincronización idempotente al recuperar conectividad.
- Respaldo de PostgreSQL, migraciones reversibles y monitoreo en el horario operativo.

## 10. Estrategia de pruebas y umbrales

| Ámbito | Verificación mínima |
|---|---|
| Motor | Factibilidad de todas las restricciones duras y comparación con línea base |
| Rendimiento | Ruta válida ≤ 45 s para 150 pedidos/15 vehículos; reoptimización ≤ 30 s |
| Escala | Carga representativa hasta 1,000 pedidos diarios y 50 vehículos |
| API | Contratos, autorización, concurrencia, errores y pruebas de integración con PostGIS |
| Frontend | Flujos críticos, modo conductor, 2G/3G simulado y WCAG 2.1 AA |
| Seguridad | Sin vulnerabilidades críticas conocidas; revisión OWASP y dependencias |
| Sostenibilidad | CPU, memoria, duración y bytes transferidos por escenario comparable |

## 11. Riesgos y mitigaciones

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Cobertura OSM insuficiente | Rutas incompletas o inviables | Auditoría territorial; corrección/entrada manual; proveedor alterno sujeto a decisión de cambio |
| Motor excede 45 s | Incumplimiento de RNF-01 | Semilla Clarke-Wright, perfilado, parada temprana, trabajador asíncrono y mejor solución factible |
| Bundle pesado en 2G/3G | Baja adopción | Presupuesto de rendimiento, división de código, compresión y carga diferida |
| Dependencias vulnerables | Exposición de datos | Versionado fijado, escaneo continuo y actualizaciones planificadas |
| Complejidad operativa prematura | Mayor costo y huella | Arquitectura modular inicial; incorporar cola/caché distribuida solo con evidencia |
| Diferencias entre ambientes | Defectos tardíos | Contenedores, variables documentadas y automatización de pruebas |

## 12. Criterios de reconsideración

La decisión se revisará únicamente si un *spike* demuestra que: (a) el motor no puede cumplir RNF-01 en el proceso propuesto; (b) la experiencia real del equipo contradice la valoración; (c) OSM no cubre el ámbito; (d) aparece una obligación normativa o institucional; o (e) el costo operativo proyectado excede la línea base. Toda sustitución exige ADR, nueva matriz y actualización del C4.
