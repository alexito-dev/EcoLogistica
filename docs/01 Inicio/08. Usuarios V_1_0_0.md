## 2. Objetivo y principios

Definir quién utiliza EcoLogística Huancayo, qué necesita, qué puede hacer y bajo qué condiciones. El modelo combina **RBAC** (permisos por rol) con **ABAC** (condiciones por propiedad, estado, fecha, distrito y finalidad), aplica mínimo privilegio y separa operación, aprobación, administración y auditoría.

La autenticación/autorización RF-11.1 y la auditoría RF-11.2 son requisitos derivados: amplían transversalmente la línea base funcional RF-01–RF-10 para hacer ejecutables los permisos definidos aquí. No representan nuevas capacidades de negocio ni modifican la prioridad de los RF originales.

Las personas descritas son perfiles, no individuos reales. No se publicarán DNI, teléfonos, domicilios ni credenciales. El diseño considera conectividad 2G/3G, teléfonos de bajo costo, español peruano claro y distintos niveles de alfabetización digital.

## 3. Perfiles primarios

### 3.1. Administrador del sistema — USR-ADM

| Dimensión | Descripción |
|---|---|
| Propósito | Mantener identidades, permisos, parámetros maestros, vehículos y conductores |
| Contexto | Oficina; navegador de escritorio; conectividad estable |
| Conocimientos | Administración operativa y conceptos básicos de seguridad |
| Necesidades | Altas/bajas controladas, trazabilidad, prevención de duplicados y configuración sin editar código |
| Riesgos | Privilegios excesivos, borrado accidental, exposición de datos personales |
| Diseño | Confirmación para acciones sensibles, historial, mínimo privilegio y sin acceso automático a secretos |

**Historia principal:** Como administrador, quiero gestionar usuarios, vehículos, conductores y parámetros autorizados para mantener el sistema disponible sin intervenir el código.

### 3.2. Planificador / despachador — USR-PLA

| Dimensión | Descripción |
|---|---|
| Propósito | Preparar la jornada, optimizar, revisar, aprobar y reoptimizar rutas |
| Contexto | Presión de tiempo entre 05:00 y 22:00; múltiples pedidos y excepciones |
| Conocimientos | Alto conocimiento de calles, clientes y operación; conocimiento digital medio |
| Necesidades | Importación rápida, causas de infactibilidad, comparación, mapa y control humano |
| Riesgos | Aprobar una ruta inviable, confundir dato automático con reporte manual, sobrescribir una ruta activa |
| Diseño | Restricciones duras, versionado, comparación previa y avisos con fuente/vigencia |

**Historia principal:** Como planificador, quiero convertir pedidos y recursos disponibles en rutas factibles y explicables para despachar a tiempo y responder a incidentes.

### 3.3. Conductor — USR-CON

| Dimensión | Descripción |
|---|---|
| Propósito | Seguir su ruta, identificar la siguiente parada y comunicar avance o incidencias |
| Contexto | Campo, luz variable, ruido, movimiento y conectividad intermitente |
| Conocimientos | Experiencia vial local; alfabetización digital variable |
| Necesidades | Pantalla simple, botones grandes, alto contraste, poco texto, operación sin red y datos mínimos |
| Riesgos | Distracción al conducir, ruta ajena, pérdida de eventos o instrucciones ambiguas |
| Diseño | Interacción solo con vehículo detenido, modo conductor, ruta propia, caché local y sincronización idempotente |

**Historia principal:** Como conductor, quiero ver únicamente mi ruta y registrar hitos con pocos pasos, incluso sin señal, para completar la jornada sin perder información.

### 3.4. Gerente / patrocinador — USR-GER

| Dimensión | Descripción |
|---|---|
| Propósito | Evaluar puntualidad, costo, distancia, combustible y CO₂ para tomar decisiones |
| Contexto | Consultas periódicas y revisión ejecutiva, no operación minuto a minuto |
| Conocimientos | Negocio y finanzas; no requiere conocer la metaheurística |
| Necesidades | KPIs comparables, supuestos visibles, tendencias y reportes PDF |
| Riesgos | Interpretar proyecciones como resultados certificados o acceder a detalle personal innecesario |
| Diseño | Agregación, unidades/fuentes, advertencias y privacidad por defecto |

**Historia principal:** Como gerente, quiero comparar la operación con la línea base para decidir acciones basadas en ahorro, servicio y sostenibilidad verificables.

### 3.5. Auditor / docente evaluador — USR-AUD

| Dimensión | Descripción |
|---|---|
| Propósito | Verificar requisitos, decisiones, cálculos, accesos y evidencia académica |
| Contexto | Revisión posterior, consultas filtradas y exportación de evidencia |
| Conocimientos | Calidad, gestión, seguridad o evaluación académica |
| Necesidades | Solo lectura, trazabilidad completa, fuentes, versiones y resultados reproducibles |
| Riesgos | Convertir el acceso de auditoría en una vía de modificación o exposición masiva |
| Diseño | Rol independiente, exportación registrada y datos personales enmascarados |

**Historia principal:** Como auditor, quiero reconstruir quién hizo qué, con qué datos y qué resultado obtuvo, sin poder alterar la evidencia.

## 4. Perfiles secundarios

| Perfil | Interacción prevista | Alcance PMV |
|---|---|---|

## 5. Jornadas de uso resumidas

| Jornada | Secuencia esperada | Resultado |
|---|---|---|
| Preparar despacho | Planificador importa pedidos → corrige errores → selecciona recursos → ejecuta optimización → revisa no asignados → compara → aprueba | Plan versionado y factible |
| Ejecutar ruta | Conductor descarga su ruta → consulta siguiente parada → registra llegada/entrega o incidencia → sincroniza | Estado actualizado sin duplicación |
| Atender incidente | Conductor/planificador registra evento → sistema propone reoptimización → planificador compara → aprueba | Nueva versión sin alterar entregas cerradas |
| Evaluar operación | Gerente filtra periodo/distrito → revisa KPIs → genera reporte | Decisión sustentada en métricas y supuestos |
| Auditar | Auditor filtra trazas → contrasta versión, parámetros y resultado → exporta evidencia | Reconstrucción reproducible y de solo lectura |

## 7. Políticas ABAC

| ID | Atributos / condición | Decisión de acceso | RF/RNF |
|---|---|---|---|
| ABAC-01 | `usuario.estado = activo` y sesión válida | Requisito previo para toda acción; denegar por defecto | RF-11.1; RNF-05 |
| ABAC-02 | `conductor.id = ruta.conductor_id` y ruta vigente | El conductor solo consulta y actualiza su propia ruta asignada | RF-08.3 |
| ABAC-03 | Pedido en estado `pendiente` o `observado` | El planificador puede editarlo; tras despacho solo registra cambio mediante incidencia/versionado | RF-02.1, RF-07.1 |
| ABAC-04 | Ruta `propuesta`, sin violaciones duras, dentro del ámbito del planificador | Se habilita aprobación; de otro modo se deniega | RF-03.5 |
| ABAC-05 | Ruta `en_ejecución` y evento pertenece a la ruta | Conductor o planificador registra hito; entregas cerradas quedan inmutables | RF-07.2, RF-08.3 |
| ABAC-06 | Distrito/centro operativo pertenece a `usuario.ambitos` | Se limita consulta y escritura; gerente/auditor pueden recibir agregados autorizados | RF-05.2 |
| ABAC-07 | Dato personal con finalidad vigente y permiso específico | Se muestra el mínimo; en reportes gerenciales/auditoría se enmascara cuando el detalle no sea necesario | RNF-19 |
| ABAC-08 | Preferencia con consentimiento vigente y no revocado | Puede usarse en nueva planificación; de lo contrario se ignora | RF-09.1 |
| ABAC-09 | Parámetro de emisión/costo con fuente y vigencia | Puede activarse; cambio exige versión, motivo y auditoría | RF-05.1, RF-10.1, RNF-17 |
| ABAC-10 | Reporte solicitado dentro del periodo y ámbito autorizados | Puede generarse; toda exportación se audita | RF-06.1, RF-11.2 |
| ABAC-11 | Incidente creado por conductor | Queda como reportado; solo el planificador puede validarlo y aprobar el cambio de plan | RF-07.1–07.2 |
| ABAC-12 | Usuario técnico sin autorización operativa explícita | No accede a datos de negocio; soporte usa registros minimizados y enmascarados | RNF-05, RNF-19 |

## 8. Segregación de funciones y controles

- Quien administra identidades no obtiene por defecto permiso para aprobar rutas ni exportar reportes de negocio.
- El conductor no puede reasignarse, alterar restricciones, cerrar entregas ajenas ni aprobar una reoptimización.
- El auditor no puede crear, modificar, aprobar o eliminar información.
- Ningún rol puede borrar trazas desde la aplicación.
- Los cambios de rol, parámetros de CO₂/costo y asignaciones se versionan y auditan.
- Para el PMV, una misma persona podrá portar más de un rol solo mediante asignación explícita; el sistema evalúa cada permiso y conserva el rol efectivo usado.

## 9. Necesidades de accesibilidad y contenido

| Necesidad | Decisión de diseño | Criterio |
|---|---|---|
| Baja alfabetización digital | Verbos directos, una acción primaria por pantalla, icono acompañado de texto | ≥ 85 % de éxito en tareas críticas |
| Visión reducida o luz exterior | Contraste AA, zoom 200 %, objetivos táctiles ≥ 44 × 44 px | Auditoría WCAG y prueba manual |
| Daltonismo | Estado no comunicado solo por color; texto/forma redundante | 100 % de estados críticos con segunda señal |
| Dificultad motora | Navegación por teclado y controles separados | Sin trampa de teclado; foco visible |
| Red inestable | Ruta descargable, lista textual alternativa y cola local | Eventos sincronizados una sola vez |
| Seguridad vial | Aviso de no manipular en movimiento y acciones breves | Flujo crítico ≤ 3 interacciones tras abrir ruta |

## 10. Casos de abuso de permisos

| Caso | Resultado esperado |
|---|---|
| Conductor cambia el ID de ruta en la URL | Acceso denegado, sin revelar existencia o datos, intento auditado |
| Planificador intenta aprobar una ruta infactible | Acción bloqueada con causas; propuesta conservada para análisis |
| Gerente solicita datos personales no necesarios | Solo recibe agregados o valores enmascarados |
| Administrador intenta borrar auditoría | Operación inexistente/denegada y evento registrado |
| Auditor intenta modificar parámetros | Denegación por solo lectura |
| Usuario inactivo conserva una sesión antigua | Sesión revocada en la siguiente validación |

## 11. Validación de perfiles y permisos

La validación incluirá: revisión de perfiles con representantes o sustitutos equivalentes; prueba de cinco tareas del conductor; pruebas positivas y negativas por cada celda sensible de RBAC; y pruebas de propiedad, estado y ámbito para cada política ABAC. Toda discrepancia se registrará como cambio de requisito, sin ampliar privilegios de forma implícita.
